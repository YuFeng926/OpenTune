# Test vectors

Vectors are machine-readable examples of OTCP exchanges. A conforming server produces responses that match them; mocks, contract tests and client tests run them. Each file holds one vector; its shape is defined by `../schemas/vector.schema.json`.

Files are named `<area>/<slug>.json`, and the vector's `id` is `<area>/<slug>`. The area is the method namespace (`session`, `job`, …).

## Common members

| Member              | Meaning                                                                                                                                                                                                                                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                | `<area>/<slug>`, equal to the file path without `.json`.                                                                                                                                                                                                                                                                                  |
| `type`              | `request` (one request and its response) or `scenario` (a sequence of steps).                                                                                                                                                                                                                                                             |
| `description`       | What the vector shows.                                                                                                                                                                                                                                                                                                                    |
| `capability`        | Capability the vector needs besides `session.v1`, which every instance reports (`session.v1` itself when it needs no other). A runner skips a vector whose capability the instance does not report, and reports it as skipped with that reason. It decides this from the capabilities the instance reports before it establishes `given`. |
| `extraCapabilities` | Optional. Further capabilities the vector needs, for example those of the methods a scenario calls to prepare state. A runner skips the vector unless the instance reports `capability` and all of these, decided, like `capability`, from the capabilities the instance reports before it establishes `given`.                           |
| `since`             | Protocol version (`MAJOR.MINOR`) the vector applies from. A runner skips vectors newer than the session's version.                                                                                                                                                                                                                        |
| `session`           | `authenticated`: before the vector starts, the runner opens the main connection and completes `session.hello` with the discovery token, using a request id different from those in the vector. `unauthenticated`: the runner only opens the main connection.                                                                              |
| `given`             | Optional preconditions (below).                                                                                                                                                                                                                                                                                                           |
| `endsSession`       | Optional. true when the vector ends the instance under test: once its last step is done, the instance quits by itself ("Vectors that end the instance", below). Default false.                                                                                                                                                           |

## Request vectors

| Member            | Meaning                                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `method`          | The method of `request`.                                                                                                  |
| `request`         | The request object to send. May contain `$ref` matchers, which the runner replaces by bound values.                       |
| `paramsValid`     | false when `request.params` deliberately violates the method's params schema. Default true.                               |
| `response`        | The expected response. May contain matchers.                                                                              |
| `connectionAfter` | `open`: the server keeps the connection open after the response. `closed`: the server closes it right after the response. |

The runner sends `request` as one line, reads one line, matches it against `response`, and then checks `connectionAfter`.

## Scenario vectors

A scenario has `steps`, run in order. Each step is an object with exactly one of these members, plus an optional `connection` naming the connection it applies to (default `main`, opened before the first step):

| Step                                                                                | Meaning                                                                                                                                                                                                                                                        |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{"connect": "<name>"}`                                                             | Open a new connection to the instance under that name. It starts unauthenticated.                                                                                                                                                                              |
| `{"send": <value>}`                                                                 | Send the value, after replacing `$ref` matchers, serialized as one compact JSON line followed by LF.                                                                                                                                                           |
| `{"sendRaw": "<text>"}`                                                             | Send the text exactly as UTF-8 bytes, with no LF added. For malformed input.                                                                                                                                                                                   |
| `{"sendHex": "<hex>"}`                                                              | Send the bytes written as pairs of hexadecimal digits, with no LF added. For input that is not valid UTF-8.                                                                                                                                                    |
| `{"sendFilled": {"head": "<text>", "fill": "<c>", "bytes": <n>, "tail": "<text>"}}` | Send `head`, then the single ASCII character `fill` repeated until `head` and the fill together are exactly n bytes long (n is not less than the length of `head`), then `tail`, all as UTF-8 with no LF added. For input too long to write out.               |
| `{"expect": <value>}`                                                               | Read the next line on the connection and match it against the value.                                                                                                                                                                                           |
| `{"expectClosed": {"noBytes": <boolean>, "withinMs": <n>}}`                         | The server closes the connection. With `noBytes` true, it sent no byte on this connection since the previous step. With `withinMs`, the close happens within n milliseconds of the end of the previous step. Without `withinMs`, runners wait up to 5 seconds. |
| `{"pauseMs": <n>}`                                                                  | Wait n milliseconds.                                                                                                                                                                                                                                           |

When the last step is done, the runner closes every connection of the vector; lines it has not read are ignored. Responses are read in the order the server sends them on a connection, so a vector expects a response only where its position is certain.

## Matchers

OTCP messages never contain member names that start with `$`. Inside `request`, `response`, `send` and `expect`, an object whose member names all start with `$` is a matcher; an object that mixes `$` names with other names is invalid. Values that are not matchers match by JSON equality (numbers by numeric value).

| Matcher                     | Matches                                                                                                                                                                          |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{"$any": true}`            | Any value, including null. The member must be present.                                                                                                                           |
| `{"$any": "<type>"}`        | Any value of that JSON type: `string`, `number`, `integer`, `boolean`, `object`, `array` or `null`.                                                                              |
| `{"$approx": x, "$tol": t}` | A number within t of x (inclusive). `$tol` defaults to 1e-6.                                                                                                                     |
| `{"$capture": "<name>"}`    | Any value; binds it to the name for later steps. May be combined with `$any` or `$approx` to constrain the value. Binding a name that is already bound makes the vector invalid. |
| `{"$ref": "<name>"}`        | In expected values: a value equal to the bound value. In values to send: replaced by the bound value. Referring to an unbound name makes the vector invalid.                     |

Matching rules:

1. An expected object matches an actual object when every expected member is present and matches. Members that are present only in the actual object are allowed, because newer minor versions may add members (PROTOCOL.md section 2.3); runners additionally validate every actual result against the method's result schema of the session's version.
2. Arrays match element by element and must have the same length.
3. Names are `[A-Za-z][A-Za-z0-9_]*`, optionally with one `.` part. Names with the prefixes `discovery.` and `runner.` are bound by the runner:
   - `discovery.<member>`: the member of the discovery file of the instance under test, for example `discovery.token`, `discovery.instanceId`, `discovery.build`.
   - `runner.wrongToken`: a value generated at run time with the same length as the discovery token, which differs from it. Vectors never contain real or fake secrets.
   - `runner.unknownContentId`, `runner.unknownPlacementId`: handles of valid form, of the instance under test and its current content epoch, that name nothing.
   - `runner.staleContentId`, `runner.stalePlacementId`: handles of valid form whose instance part differs from that of the instance under test.
   - `runner.lastTrackId`: the `trackId` of the last track slot of the instance under test (the last entry of `project.get` `tracks`).
   - `runner.unknownTrackId`: a `trackId` that names no track slot of the instance under test: `runner.lastTrackId` + 1.
   - `runner.arrangementRevision`: the `arrangementRevision` of the instance under test once the preconditions are established (`project.get`), for requests that must name it.
   - Names that `given` establishes (below).
4. Where an expected response has a number `id`, the runner also checks how the received line writes it: as a plain integer literal, without a fraction, an exponent or a sign (PROTOCOL.md section 3.3 rule 3). The runner reads the literal from the top-level `id` member of the line. This is the only check of how a value is written; everywhere else numbers match by value.

## Preconditions (`given`)

`given` describes state the runner establishes before the vector starts, by means specific to the target (a mock creates it directly; a real instance may need preparatory calls). A runner that cannot establish a precondition reports the vector as skipped with the reason.

| Member                | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `jobs`                | `[{bind, kind, state, cancellable, error}]`: a job of that kind exists in that state with that `cancellable` value; its `jobId` is bound to the name `bind`. A terminal job has a result of its kind. The job keeps its state and progress while the vector runs, unless a request of the vector changes it. `error` (`{kind, reason}`), for a failed or cancelled job, gives the kind and reason of the job's `error`. A running export job holds the export lock.                                                                                                                                                                                                                                                |
| `withoutCapabilities` | Capabilities the instance does not report while the vector runs. The runner removes them when it establishes `given`, after it has decided from `capability` and `extraCapabilities` that the vector applies, so an instance that never reports such a capability runs the vector as well. Used to test `UNSUPPORTED(capability_missing)`.                                                                                                                                                                                                                                                                                                                                                                         |
| `editingScheme`       | The editing scheme selected in OpenTune's preferences: `openTune` or `openDyne` (PROTOCOL.md section 21).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `dirty`               | The project's unsaved-changes flag when the vector starts.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `clips`               | The project contains exactly these clips, each a placement with a content of its own (below), and with `clipOnEveryTrack` the clips it adds.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `clipOnEveryTrack`    | `true`: every track slot of the instance that no clip of `clips` is on holds one more clip, 2 seconds long at timeline 0 with analysis `ready` and no notes, which no name binds. Used where every track must hold clips, whatever the number of track slots.                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `files`               | Files and paths the runner provides (below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `history`             | `{undo, redo}`: the undo and redo histories consist of exactly these entries (below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `visibleTrackCount`   | The number of track slots shown, counted from track 0, or `all` for every slot. Clips of `clips` may lie on hidden tracks.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `dialogs`             | The dialogs open in OpenTune, from the bottom of the stack to the top (below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `onboarding`          | The first-run onboarding: `notShown` (it was never shown and is not showing; while the vector runs, OpenTune does not start it by itself), `shown` (it was shown before) or `showing` (the overlay is on screen and onboarding is not yet marked as shown, which OpenTune does once the overlay shows its choice).                                                                                                                                                                                                                                                                                                                                                                                                 |
| `keyboardFocus`       | Where the keyboard focus of the OpenTune window is. `tempoField`: the tempo field of the transport bar holds it, as in a window that has just started in the foreground; a switch of the view then moves the focus out of the field, and the field writes back the tempo it shows (PROTOCOL.md section 14.6). `tempoField` is the only value of this version. Without the member the vector assumes nothing about where the keyboard focus is, so a vector that depends on the field holding it names it. A runner that cannot make the field hold the focus (a started OpenTune whose window may be in the background, which the runner does not control) reports the vector as skipped with that reason.         |
| `gpu` | Whether OpenTune can create its inference session on the GPU. `unavailable`: it cannot, so OpenTune runs on the CPU whatever the rendering priority is, and `session.info` reports `processing.backend` `cpu`; a change of the rendering priority to `gpuFirst` then falls back to the CPU. `available`: it can, so under `gpuFirst` the backend is the GPU's. Without the member a vector assumes nothing about the GPU. A runner that cannot control the GPU (a started OpenTune on a machine whose GPU the runner does not control) reports the vector as skipped with that reason. |
| `preferences`         | `{tuningHz, hybridMode, experimentalFeatures, vocoderWeight, renderingPriority, f0Model, options, recentProjects}`, each optional: user-global preferences. `options` is `{vocoderWeight, f0Model}`: the weight files and the pitch models that the installation offers, which `prefs.get` lists in `processing.options`; `vocoderWeight` and `f0Model` name one of them. The other list is fixed: `gpuFirst`, `cpuFirst`. `recentProjects` names given files (`files`), the most recent first.                                                                                                                                                                                                                    |
| `projectFile`         | The `bind` of a given file (`files`, extension `.otproj`) that is the current project's file: the project, as the other members describe it, was last saved to it. Without `projectFile` the project was never saved.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `audio`               | `{running, failsToOpen, asioRateRestoreFails, alternatives}`: with `running` true an audio output device runs at 44100 Hz with a buffer of 512 frames and output channel pair 0, and also offers 48000 Hz and a buffer of 256 frames; it offers no other output channel pair. With `running` false no audio device is open. With `failsToOpen` true the device fails to open with any changed setup. With `alternatives` true (it needs `running` true) the machine also offers another device type that has an output device and another output device of the current type, and the runner binds `audio.deviceType` and `audio.outputDevice` (the current ones) and `audio.otherDeviceType` and `audio.otherOutputDevice` (the others). With `asioRateRestoreFails` true (it needs `running` true) OpenTune cannot restore the sample rate of an ASIO device before the device type or the output device is switched: the switch goes on, and the result carries the warning `ASIO_RATE_NOT_RESTORED`. A runner that cannot make the restoration fail reports the vector as skipped with that reason. |

Each entry of `clips` is `{bind, trackId, startTimelineSec, durationSec, analysis, notes, key, pitchShift, timeGrid, fadeInSec, fadeOutSec}`; the last six members are optional. The runner creates the clip from a mono WAV file of `durationSec` seconds with a voiced pitch (silence when `analysis` is `unvoiced`). The clip starts at `startTimelineSec` on track `trackId`, shows its whole content, and has gain 1 (0 dB), a fade-in of `fadeInSec` and a fade-out of `fadeOutSec` seconds (by default no fades).

- `analysis`: `ready` (pitch analysis finished with voiced frames), `running` (requested and not finished while the vector runs), `failed` (failed for a reason other than silence) or `unvoiced` (finished without voiced frames).
- `notes`: the content's notes, `[{startContentSec, endContentSec, targetMidi}]` in start-time order, with OpenTune's default note parameters and no cent offset; only with `analysis` `ready`. Without `notes` the content has no notes.
- `key`: the content's key, `{root, scale}`. Without it, the key is the one the analysis detected.
- `pitchShift`: `{semitones, cents}`; without it, 0 and 0.
- `timeGrid`: the handles of the content's time grid, `[{bind, contentSec}]`, each at the same output time as content time; `bind` names the handle's `handleId`. Without `timeGrid` the grid has no handles.

For a clip bound as `clip`, the runner binds `clip.contentId`, `clip.placementId`, `clip.sourcePath` (the source file) and the tokens after all preconditions are established: `clip.revision`, `clip.gridRevision`, `clip.keyRevision` and `clip.geometryHash`.

Each entry of `files` is `{bind, kind, extension, durationSec}`. The runner binds `bind` to an absolute path in the form PROTOCOL.md section 20.1 requires, ending in `extension` (default `.wav`):

- `audio`: an existing mono WAV file of `durationSec` seconds with a voiced pitch;
- `absent`: a path in an existing, writable directory where no file of that name exists;
- `existing`: an existing file. The runner also binds `<bind>.next` to the path `<stem> (2)<extension>` in the same directory, where `<stem>` is the file name without its extension, and makes sure that no file exists there: the name an export with `ifExists` `rename` writes (PROTOCOL.md section 19 rule 3). For this kind `bind` has no `.` part;
- `noAccess`: a path in a directory that the instance cannot open, so that it cannot determine the identity of a file there (PROTOCOL.md section 20.3). How a runner makes such a directory depends on the system: on POSIX systems by its permissions, on Windows by an access control list that denies the instance's user, which a runner may not be able to set without rights it lacks. A runner that cannot create one reports the vector as skipped with that reason, as for any precondition it cannot establish;
- `undecodable`: an existing file whose content is not audio that OpenTune can decode, and, with the extension `.otproj`, not a project that OpenTune can read;
- `project`: a project file (extension `.otproj`) that OpenTune can open. It holds one clip on track 0 at timeline 0 that shows the whole of a mono WAV file of `durationSec` seconds with a voiced pitch, which exists next to the project file;
- `projectMissingMedia`: the same project file, except that the WAV file it references does not exist.

Each entry of `history.undo` and `history.redo` is `{bind, origin, action, clip, trackDeletedAfter, laterTrackDeletedAfter}`, oldest first, so the last entry is the top. `origin` is `control` (made through this API) or `ui`; `action` (`noteEdit`, `pitchShift`, `clipMove` or `clipSplit`) was applied to the clip with that `bind`; `clipMove` moved the clip in time on its track. With `trackDeletedAfter` true, a track before the clip's track was deleted after the entry was recorded, so the clip's track position (its `trackId` in `clips`) is one less than when the entry was recorded. With `laterTrackDeletedAfter` true, a track after the clip's track was deleted after the entry was recorded, so the clip's track did not move. `bind`, for a `control` entry, names its `undoId`. The clips are in the state after the `undo` entries and before the `redo` entries.

Each entry of `dialogs` is `{kind, trackId, colour}`: `trackColour` (the track-colour dialog of track `trackId`, showing the colour `colour`, which differs from the track's colour), `confirm` (a confirmation dialog), `pitchShift` (the pitch-shift dialog), `preferences` (the preferences window), `message` (a message dialog) or `unknown` (a dialog that the server cannot classify, so `ui.getState` reports it with `closeCommits` true). Only `trackColour` has `trackId` and `colour`.

Members that `given` leaves out describe an instance that has just started with a new project: no clips, the transport stopped at timeline 0 (also `playStartTimelineSec`) with the loop flag off, 120 bpm in 4/4, the window showing the arrangement with no track active and no clip selected, no dialog and no first-run overlay showing, empty undo and redo histories, and no unsaved changes. The clips of `clips` are added without selecting them.

In every vector, the runner makes sure that the connections of the vector are the only connections to the instance while it runs, because other clients would change the numbers of connections and sessions. Later versions add precondition members together with the methods that need them.

## Vectors that end the instance

A vector with `endsSession` true ends the instance under test: its last step makes the instance quit by itself (`app.quit`). The format and the runners treat it as follows.

1. A request vector with `endsSession` true has `connectionAfter` `closed`: the server closes every connection when it stops (PROTOCOL.md section 3.6 rule 2). A scenario with `endsSession` true ends with a response of the quitting call, and an `expectClosed` step may follow it. In a vector with `endsSession` true, a wait for a close (`connectionAfter` `closed`, and `expectClosed` without `withinMs`) is 15 seconds instead of 5, because the instance first finishes its own shutdown.
2. A vector whose method could quit the instance but is refused (`UNSAVED_CHANGES`, `BUSY`) does not have `endsSession`: it shows that the instance still runs, and as a request vector it has `connectionAfter` `open`, whose probe proves that.
3. When the last step is done, the vector is not complete until the instance has ended, and the runner checks that within 15 seconds after the last step: the server has closed every connection of the vector; no connection to the instance's port is accepted any more; the discovery file of the instance has been removed (PROTOCOL.md section 5.4 rule 1); and, when the runner started the process itself, the process has exited by itself with exit status 0. Whatever of this the runner cannot observe for the target it runs against (for example the exit status of a process that it did not start) it leaves out, and its report says so. A check that fails fails the vector. The runner never ends the instance itself while it waits.
4. The runner does not use the instance again. This format chooses to restart the target rather than to order the vectors: after a vector with `endsSession` true the next vector gets a new instance. A runner that gives every vector an instance of its own, as the runners of this repository do, needs nothing more than the check of rule 3. A runner that shares one instance between several vectors starts a new instance after every vector with `endsSession` true, and runs no other vector against the ended one.
5. Preconditions (`given`) of such a vector are established like those of any other vector. A runner that cannot establish them, or whose target must not be quit, skips the vector with that reason; a skipped vector is not a failure.

## Reproducibility

Vectors are written so that they hold against any target: mock, a window-less test build of OpenTune, or a running OpenTune. In a window-less test build the methods that act through the editor window fail with `UNSUPPORTED(no_editor_window)` (PROTOCOL.md section 7 rule 6), so a runner gives such a build a stand-in for the editor or skips their vectors. Values that differ between runs (ids, timestamps, secrets) are matched with `$any`, `$capture` and `$ref`, never written as literals.

A mock used for contract tests SHOULD additionally be deterministic, so that its full transcripts can be compared byte for byte:

1. `--seed <n>` seeds every random choice the mock makes, except the token and the server proof, which always come from a cryptographically secure generator and are read from the discovery file.
2. A fixed `instanceId` can be configured, so that `contentId`, `placementId`, `undoId` and `jobId` values repeat.
3. `jobId` and `undoId` sequence numbers start at 1 and increase by 1.
4. The clock is injectable: timestamps and timeouts come from it, so that tests of waits and timeouts do not depend on real time.

## Coverage

1. Every method with a defined schema has at least one success vector.
2. Each of these session-layer behaviours has at least one vector:
   - before authentication (PROTOCOL.md sections 3.4 and 3.5): a first line that is not a `session.hello` request (an HTTP request; another method); no complete line within `helloTimeoutMs`; no LF within `preAuthReadBytes`; more than `maxPreAuthConnections` waiting connections;
   - `session.hello` (sections 4.2 and 4.4): success; `AUTH_FAILED` for a wrong and for a malformed token; `PROTOCOL_MISMATCH`, also for a hello shaped by another major; `INVALID_ARGUMENT(invalid_params)` with the right token; `BUSY(session_limit)`; `INVALID_ARGUMENT(hello_repeated)`;
   - every case of section 3.3 rule 5 that does not run a method: `line_too_long`, ignored blank lines (and a CR before the LF), `parse_error` (invalid JSON, invalid UTF-8, a string that escapes a lone surrogate, nesting deeper than 64), `batch_unsupported`, an ignored notification, `invalid_request` (also for a `method` that is missing or not a string), `duplicate_id`, `BUSY(request_limit)`, `UNSUPPORTED(unknown_method)` (also for a name without a namespace and for the empty string), `UNSUPPORTED(capability_missing)` and `INVALID_ARGUMENT(invalid_params)`;
   - request ids (section 3.3 rule 3): number ids written with a fraction or an exponent, the bounds of number ids, string ids measured in code points, ids that are not valid, and the plain integer literal in responses, also in a fixed response.
3. Behaviours that need long real-time waits or a stopping server (the idle timeout, `TIMEOUT(dispatch_timeout)`, `SHUTTING_DOWN`) have no vectors in this version; implementations test them with an injectable clock and their own shutdown tests. The one exception is the instance that `app.quit` ends: vectors with `endsSession` show that it ends and what it leaves behind ("Vectors that end the instance"). A request sent to an instance in the stopping state is still not shown, because the instance closes the connection within a few milliseconds and no vector can expect an answer at a position that is certain.
4. Every error vector's kind and reason are registered, and its `code` and `message` follow PROTOCOL.md section 17.
5. Handle kinds (PROTOCOL.md section 9 rule 1): a `placementId` passed where a `contentId` is expected, and a `contentId` passed where a `placementId` is expected, get `INVALID_ARGUMENT(invalid_params)` (`content/get-notes-handle-kind`, `export/start-handle-kind`).
6. Every value of the params members `op`, `mode`, `kind`, `layout`, `action` and `target` of a method with a defined schema is sent by at least one success vector.
7. Every error kind in a method's `x-otcp.errors` other than the generic ones of `../methods/README.md` (`INVALID_ARGUMENT`, `UNSUPPORTED`, `BUSY`, `TIMEOUT`, `SHUTTING_DOWN` and `INTERNAL`) has a vector in which that method returns it. Every kind in `x-otcp.jobErrors` other than `CANCELLED` and `INTERNAL` has a vector in which a job of the method's job kind ends with it. Where a vector can make a job fail through the protocol, it does so. A failure that no request can bring about, or only after a long wait (for example a change made in the OpenTune UI while an export writes its file, which the export lock keeps requests from making, a failing render block, the export wait of 120 s, or the wait of a `prefsApply` job for the vocoder), is shown with a job that `given.jobs[].error` establishes; such a vector shows only how `job.get` reports the error, and implementations test the behaviour that produces it in their own tests. A direct error that only a fault of the installation brings about (`MODEL_UNAVAILABLE(model_missing)` of `prefs.set`, since the only pitch model is also the one in use and a request for it is a no-op) has no vector; implementations test it in their own tests.
8. Every write method has a success vector whose expected result lists every member of the write envelope (PROTOCOL.md section 14.1), with `revisionDiff`, `undo` and `dirty` written out rather than left to a matcher. An expected job result that is a write envelope is written out in the same way, or left to a matcher as a whole. Other expected results of scenario steps may list only some members (matching rule 1), for example where a step only prepares or captures state. `app.quit` is the one write method without an envelope (PROTOCOL.md section 14.1): its success vectors list every member of its own result (`quitting`, `discardedUnsavedChanges`, `projectPath`, `exitDeadlineMs` and `warnings`), with `warnings` written out.
