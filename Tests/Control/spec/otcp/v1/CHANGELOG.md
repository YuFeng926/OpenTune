# Changelog

All notable changes to the OTCP specification are recorded here. Versions follow `MAJOR.MINOR.PATCH` (README.md, "Versions"); each released version is tagged `spec-v<version>`.

## [1.0.0] - 2026-11-01

First release of protocol major 1. The text is that of `1.0.0-rc.9`, except for the status, four sentences that referred to the release candidate and one example (below). The wire version stays `1.0`, and no method, param, result member, capability, error kind, reason or warning is added, removed or changed, so a client or server of rc.9 is a client or server of 1.0.0. From this version on, the rules of PROTOCOL.md section 2 apply to every change: a patch changes only wording, examples and vectors, a minor version only adds, and a removal, a rename or a change of meaning or unit needs a new major version.

### Changed

- Status and current version `1.0.0` (PROTOCOL.md, README.md); the text no longer calls itself a draft or a release candidate.
- Two sentences that said "this release candidate" name the version they mean: an implementation of protocol major 1 may still send the export errors of PROTOCOL.md section 19 rule 11 without a reason, and a project file written by an earlier OpenTune, which kept the media of every project in a directory in one shared folder, names its media in the folder `Project_Media` (section 20.4 rule 3). Neither rule changes.
- Two sentences that announced what "a later release candidate" might change say which kind of version could change it (section 2.2): keeping the redo history after a change without an undo entry (section 15.3 rule 9) would change the rule and needs a new major version, so clients keep assuming that such a change clears the redo history; a reason of its own for the failed commit of a note of zero duration, and a warning that lets the prediction report it (section 15.4 rule 7), can come in a minor version. Neither rule changes.
- README.md: the example of how to refer to a released version names `1.0.0` and the tag `spec-v1.0.0`.

## [1.0.0-rc.9] - 2026-10-31

Ninth release candidate of protocol major 1, proposed as the text of 1.0.0. It records the behaviour of the OpenTune release that the control interface now builds on (OpenTune 1.8.2), which differs from the text in five places, and it adds what a review of the processing settings found missing: a warning for the case in which the GPU priority runs on the CPU, and descriptions for the processing fields of `session.info` and `prefs.get`. The wire version stays `1.0`. The change adds two warning codes and changes no method, param or result member, so a client of rc.8 keeps working: it accepts the warnings it does not know (PROTOCOL.md section 2.3), and a server of rc.8 does not send them. A client of rc.9 that talks to a server of rc.8 simply never receives them. One behaviour changes, though: `track.add` now marks the project as changed (the number of visible tracks is project state), so a client that relied on it leaving the project unchanged sees `dirty.after` true.

### Added

- Warning `BACKEND_FALLBACK` (`registry/warnings.json`): the result of the `prefsApply` job of `prefs.set` carries it when the call changed `renderingPriority` to `gpuFirst` and the inference backend that OpenTune reports when the job ends is `cpu`, so the GPU was requested and is not in use. `subject` is null; `data` is `{requested, actual}`: `requested` is the rendering priority the call set (`gpuFirst`) and `actual` is the backend that runs (`cpu`, the value of `session.info` `processing.backend`). The call succeeded and the preference is set; the warning only tells the client what the preference alone does not show. PROTOCOL.md section 12.7 rule 7 defines it, including that the backend is read once when the job ends, so a job that did not wait for the vocoder can still read the backend from before the change.
- Warning `ASIO_RATE_NOT_RESTORED` (`registry/warnings.json`): the result of `audio.set` carries it when the call changed `deviceType` or `outputDevice` and OpenTune could not restore the sample rate of an ASIO device before it switched. `subject` is `{"singleton": "audioDevice"}`; `data` is `{deviceName, sampleRateHz}`: the ASIO device whose rate was to be restored and the rate in Hz that OpenTune tried to restore. The switch went on and succeeded, so the call does not fail and nothing is rolled back; the warning says that the device has changed but the ASIO driver may still run at another sample rate than before.
- Vectors `prefs/set-rendering-priority-fallback` (the warning, and `session.info` showing the priority `gpuFirst` with the backend `cpu`), `prefs/set-rendering-priority-gpu` (no fall back, no warning), `audio/set-asio-rate-not-restored` (the warning after a switch of the device type) and `audio/set-asio-rate-not-needed` (a change of the buffer size restores no rate and carries no such warning).
- Vector preconditions `given.gpu` (`available` or `unavailable`: whether OpenTune can create its inference session on the GPU) and `given.audio.asioRateRestoreFails` (`schemas/vector.schema.json`, `vectors/README.md`, "Preconditions"). A runner that cannot establish them, such as the one for a started OpenTune on a machine whose GPU and audio drivers it does not control, reports the vectors as skipped with that reason.

### Changed

- `audio.set`: the restoration of the sample rate of an ASIO device before a switch of the device type or the output device is best effort, as on OpenTune's audio settings page. A failed restoration no longer stops the switch: the switch goes on and the result carries `ASIO_RATE_NOT_RESTORED` (above). Before this release candidate the text described such a failure as a failure to open the device, with the previous setup restored and `IO_ERROR(device_open_failed)`. That reason stays and keeps its meaning for a device that cannot be opened with the new setup (vector `audio/set-rollback`); no reason is retired, because the failed restoration had no reason of its own. The description of the reason names the difference.
- The media folder of a project (PROTOCOL.md section 20.4 rule 3, the description of `project.saveCopy`): OpenTune writes the media of a save, a Save As or a copy into the folder `<file name of the target without .otproj>_Media` beside the target project file, where it used to write them into one folder `Project_Media` that every project file in the directory shared. A copy to `D:\x\backup.otproj` has its media in `D:\x\backup_Media` and does not share a folder with the project it was made from. A media file is always written, through a temporary file, and replaces a file of the same name, whatever its age; before, a file that was not older than its source stayed. The case of rule 3 that the media of another project in the same directory can be replaced is gone: only a media folder of the target's own name that is already there (the target project file does not exist, the folder does) has files of the same names replaced. `project.saveCopy` still decides `ALREADY_EXISTS(target_exists)` by the project file alone, and a media folder that exists is no conflict. A client that writes many copies counts the space, because each copy now holds a complete set of the media. A project file written before this release candidate names its media in `Project_Media` and opens from there; the next save writes `<name>_Media`.
- `export.start` (PROTOCOL.md section 19 rules 6 and 7, the description of the method, the reason `export_wait_timeout`): OpenTune drains the render blocks that it has set aside for a delayed retry before it exports, and an export for which they cannot be drained fails. This is render work pending of rule 6, so the job waits for it, and when it cannot be drained the job fails with the existing retryable `NOT_READY(export_wait_timeout)`. No reason is added: the existing one already means that analysis and rendering did not settle in time, and a client already waits and exports again.
- The `description` of an undo entry (`undoable.description` and `historyEntry.description` of `schemas/common.schema.json`, PROTOCOL.md section 15.1, `edit.getHistory`): it is the text that the undo menu of the OpenTune window shows for the entry, and since the upstream release it follows the language of the OpenTune interface. Clients show it and do not parse, compare or build on its wording. No vector asserted a wording (they use `$any` `string`), so none changes.
- Field descriptions: `session.info` `processing.backend` (the detector's current choice, which after a fall back can differ from `renderingPriority`, and which reports `cpu` also when nothing has been detected), `processing.vocoderReady` (`false` is normal before the first time a render needs the vocoder), `processing.vocoderReconfiguring`, `processing.renderingPriority` and `prefs.get` `processing.options.renderingPriority` (the meaning of `gpuFirst` and `cpuFirst` and how a change takes effect). The description of `prefs.set` no longer says that `renderingPriority` "only changes the inference backend and never does", which was unfinished; it says that the change is not audible and never reports `reRenderQueued`, and names `BACKEND_FALLBACK`.
- The number of visible tracks is project state, not view state. OpenTune 1.8.2 saves it in the project file and restores it when the project is opened; the text of rc.8 called it view state that is not saved. PROTOCOL.md section 15.2 rule 6 no longer lists it as view state, so rules 1 and 2 and the dirty flag (section 15.5) apply to it, and the side-effect table of section 14.6 says that the number is saved with the project. `track.add` marks the project as changed (`dirty.after` true), reports `undo` `{undoable: false, reason: no_upstream_undo, revert: null}` and the warning `IRREVERSIBLE` (subject the first track shown), where it reported the undo reason `not_persisted_state` and the warning `NOT_PERSISTED` and left the project unchanged; its description says why `track.delete` is no revert recipe (it deletes the clips on the track with it, deletes one track per request and needs the end user's consent). The warning `NOT_SAVED_IN_PROJECT` no longer lists `visibleTrackCount` in `data.items` (the registry and the descriptions of `project.save`, `project.saveAs` and `project.saveCopy`), because the project file holds it. `project.open` reports the number that the file stores in `restored.visibleTrackCount` (for a file that stores none, the number that OpenTune infers from its content), lists the tracks that the open showed in `sideEffects.tracksRevealed` (computed from the numbers before and after), and leaves the project unchanged. Behaviour change: a client written against rc.8 that relied on `track.add` not marking the project as changed now sees it changed, and a client that waited for `NOT_PERSISTED` or the undo reason `not_persisted_state` from `track.add` receives `IRREVERSIBLE` and `no_upstream_undo` instead. The wire version stays `1.0`; no member is added or removed. The vector `track/add-ok` and the five vectors that list `NOT_SAVED_IN_PROJECT` items follow.
- Status and current version `1.0.0-rc.9`.

## [1.0.0-rc.8] - 2026-10-28

Eighth release candidate of protocol major 1, proposed as the text of 1.0.0. It adds one method that writes a copy of the project to a new file without making the copy the project's file. `project.saveAs` was the only request that wrote a project to a new path, and it does what the menu entry Save As does: the new path becomes the project's file, the unsaved-changes flag is cleared and the path goes to the top of the recent-projects list. A client that wants a restore point or a periodic backup of work in progress, without touching the file the end user works with, could not get one. The wire version stays `1.0`; the change only adds, so a client of rc.7 keeps working, and a server of rc.7 does not report the new capability, so a client of rc.8 does not call the method there (PROTOCOL.md section 7 rule 1).

### Added

- Method `project.saveCopy` (layer L8, capability `project.copy`, write `yes`, result kind `write`, `since` `1.0`): params `{path}` (an absolute path ending in `.otproj`, no other member). It writes a copy of the project to `path` as a job of kind `projectCopy`, with the same steps as a save (the snapshot is taken on the main thread when the call is validated; the project file goes through a temporary file in the target directory and the final rename of section 20.4; the media go into the folder `Project_Media` beside `path`, as OpenTune does for a save). It changes none of what `project.saveAs` changes: the current project file, the unsaved-changes flag, the recent-projects list, the undo history and the window stay as they were. It never replaces a project file and has no `confirm`: when anything exists at `path`, including the current project file, the call fails with `ALREADY_EXISTS(target_exists)` and does nothing; a file that appears at `path` while the job runs fails the job with the same error, because the final rename never replaces. When whether `path` exists cannot be determined, the call fails with `IO_ERROR(read_failed)`. A project that was never saved can be copied. The busy checks are those of every write; the job is a project operation, so writes are refused with `BUSY(project_operation)` while it runs, as while a save runs. The job cannot be cancelled. Like `export.start`, the call itself changes no project state: its result is the write envelope with `applied` false that names the job. The result of the job is not a write envelope: `{path, sizeBytes, projectPath, projectDirty, warnings}` with `nullReasons` when `projectPath` is null (the project was never saved, reason `no_project_path`). `projectPath` and `projectDirty` report the project's file and the unsaved-changes flag as they are after the copy, which the copy did not change; `warnings` holds `NOT_SAVED_IN_PROJECT` with `data` `{items}`, as for a save, and neither `IRREVERSIBLE` nor an undo descriptor: the copy replaces no project file and changes no project state, and replacing an older media file of the same name in `Project_Media` is what a save does already (PROTOCOL.md section 20.4 rule 3). Errors: `INVALID_ARGUMENT` (the path, the extension, params), `ALREADY_EXISTS`, `IO_ERROR`, `UNSUPPORTED` (`capability_missing`, and `no_editor_window` while no editor exists), `BUSY`, `TIMEOUT`, `SHUTTING_DOWN` and `INTERNAL`; the job ends with `ALREADY_EXISTS`, `IO_ERROR` (`write_failed`, also for a media file that cannot be copied) or `INTERNAL`, deletes its temporary file and leaves no file at `path`.
- Capability `project.copy` in `registry/capabilities.json`: an instance reports it exactly when it implements `project.saveCopy`. An older instance does not report it, and a client then tells the end user that this OpenTune cannot write copies. It does not fall back to `project.saveAs`, which would make the copy the project's file.
- Job kind `projectCopy` (PROTOCOL.md section 12.3, `common.schema.json`): started by `project.saveCopy`, not cancellable. The job result is defined by the method, as for every kind (section 12.1). It is a separate kind from `projectSave` because its result is not a write envelope and the project does not change.
- Vectors `project/save-copy-ok` (the start result, written out), `project/save-copy-job` (a scenario: the job result with the project's file and flag unchanged, then `project.get` and `prefs.get` showing that the project file, the unsaved-changes flag and the list of recent projects did not change), `project/save-copy-never-saved` (a project without a file: `projectPath` null with `nullReasons`), `project/save-copy-exists` and `project/save-copy-exists-current` (`ALREADY_EXISTS(target_exists)` for another file and for the current project file), `project/save-copy-bad-extension`, `project/save-copy-no-access` (`IO_ERROR(read_failed)`), `project/save-copy-busy-modal` (`BUSY(modal_open)`), `project/save-copy-job-failures` (a failed `projectCopy` job with `IO_ERROR(write_failed)` and one with `ALREADY_EXISTS(target_exists)`) and `project/save-copy-capability-missing` (an instance of rc.7 or earlier, `UNSUPPORTED(capability_missing)`).
- PROTOCOL.md: the status line, section 7 rule 6 (`project.saveCopy` needs the editor window), section 12.3 (the job kind), section 13.2 (a copy is a project operation, also for `app.quit`), section 20.1 (extensions), section 20.2 rule 4 (no `confirm`, because a copy never replaces a project file), section 20.4 (project copies use the final rename that never replaces; new rule 3: the media written beside a save, a Save As or a copy share the folder `Project_Media`, an older media file of the same name is replaced, so in a folder that holds another OpenTune project that project's media can be replaced, as OpenTune's own save does, and a client writes copies into a folder of its own), section 22 (the capability, the layer row and the method row).

### Changed

- Registry descriptions: the reason `project_operation` and `job_in_progress` name the job kind `projectCopy`, and the warning `NOT_SAVED_IN_PROJECT` says that it is also sent when a copy was written. No code is added or renamed.
- Status and current version `1.0.0-rc.8`.

## [1.0.0-rc.7] - 2026-10-26

Seventh release candidate of protocol major 1, proposed as the text of 1.0.0. It adds a method that switches the OpenTune window between the arrangement view and the piano roll, because `ui.setSelection` could only open the piano roll and no request led back to the arrangement view. It adds a method that quits OpenTune, because an agent that has finished could save the project but could not close the application. It also removes the reference alignment: OpenTune's upstream project retired the experimental reference track and its AUTO Ref button, and the control interface no longer reads, writes or reports it. The wire version stays `1.0`. Protocol major 1 has only release candidates so far, and a release candidate may remove members; from 1.0.0 on, a minor version only adds (README.md, "Versions"). The registries still keep every capability, reason and warning code that was sent, and mark the ones that are no longer sent. A client of rc.6 that sends a removed member gets `INVALID_ARGUMENT(invalid_params)` from a server of rc.7 (PROTOCOL.md section 2.3 rule 3), and the results of a server of rc.6 carry members that a client of rc.7 does not know and ignores (section 2.3 rules 1 and 4).

### Added

- Method `ui.setWorkspace` (layer L6, capability `ui.workspace`, write `conditional`, `since` `1.0`): params `{workspace}` with `arrangement` or `pianoRoll`, no other member. It does what the two view buttons of the transport bar do, so closing the piano roll is switching to `arrangement`. Switching to `pianoRoll` shows the clip that is selected; with no clip selected the piano roll is empty, which the window allows and which is not an error. Only the view changes: `revisionDiff` is empty, `dirty` stays as it was, and nothing is generated or queued in either editing scheme. The result is a write envelope: one change (entity `ui`, `ref` `{"singleton": "workspace"}`, member `workspace {before, after}`), `sideEffects.workspaceSwitched {from, to, revert: null}` (the key and shape `ui.setSelection` uses when it opens the editor), the `workspace` member of the `ui` snapshot holding the workspace after the switch, undo reason `not_persisted_state` with a revert recipe that switches back with `ui.setWorkspace`. The workspace the window already shows is a no-op (`changes` and `sideEffects` empty, undo reason `no_op`). Errors: `INVALID_ARGUMENT` (a missing or unknown `workspace`, `executed` false), `BUSY` (the checks of every write, section 13.2: `modal_open`, `pointer_down` and the others), `UNSUPPORTED` (`capability_missing`, and `no_editor_window` while no editor exists), `TIMEOUT`, `SHUTTING_DOWN` and `INTERNAL`.
- Capability `ui.workspace` in `registry/capabilities.json`: an instance reports it exactly when it implements `ui.setWorkspace`. An older instance does not report it, and a client then tells the end user to use the view buttons of the transport bar.
- Entity name `ui` for `changes[].entity`, with the `ref` `{"singleton": "workspace"}` (PROTOCOL.md section 14.3).
- Vectors `ui/set-workspace-arrangement` (a scenario: open the piano roll with `ui.setSelection`, then switch back), `ui/set-workspace-piano-roll`, `ui/set-workspace-piano-roll-opendyne` (a scenario: select a clip in the `openTune` scheme, switch to `openDyne`, which generates the notes of the clip the piano roll holds and says so, then switch to the piano roll with `ui.setWorkspace`, which generates nothing and changes no revision, and read that the note count is the same), `ui/set-workspace-noop`, `ui/set-workspace-invalid` and `ui/set-workspace-busy-modal`.
- PROTOCOL.md: the status line and section 7 rule 6 (`ui.setWorkspace` needs the editor window), section 14.3 (entity `ui`), section 14.6 (a paragraph on how the workspace changes), section 22 (the capability, the layer row and the method row).
- Method `app.quit` (layer L8, capability `app.quit`, write `yes`, result kind `plain`, `since` `1.0`): params `{discardUnsaved?}` (boolean, default false, no other member). It quits OpenTune as the close button of the OpenTune window does, which saves the plugin state and ends the application; the window asks nothing about unsaved changes and quits at once, and this method does not. The checks run in this order and the first that fails ends the call with `executed` false: the server is stopping (`SHUTTING_DOWN`); OpenTune is busy (`BUSY`: the checks of section 13.2, and in addition any job that has not reached a terminal state, with `import_in_progress`, `export_in_progress` or `project_operation` for the job kinds that section names and `job_in_progress` for the others); the project has unsaved changes and `discardUnsaved` is not true (`UNSAVED_CHANGES(project_dirty)`). `discardUnsaved` follows section 20.2 rule 3 like the one of `project.open`: clients set it only when the end user explicitly agreed to lose the changes. When no check fails the server answers first, then enters the stopping state (a later request gets `SHUTTING_DOWN`, connections close, section 3.6 rule 2), then saves the plugin state and ends the application through the normal shutdown, which deletes the discovery file. The result is `{quitting, discardedUnsavedChanges, projectPath, exitDeadlineMs, warnings}` (`nullReasons` when `projectPath` is null because the project was never saved); `warnings` holds `IRREVERSIBLE` (subject `{"singleton": "project"}`) when unsaved changes were discarded. It is not a write envelope: the process ends right after it, so there is no version vector to compare, no tokens and no undo, and the call cannot be reverted. PROTOCOL.md section 14.1 names this exception. Errors: `INVALID_ARGUMENT`, `UNSAVED_CHANGES`, `UNSUPPORTED` (`capability_missing`, and `no_editor_window` while no editor exists), `BUSY`, `TIMEOUT`, `SHUTTING_DOWN` and `INTERNAL`.
- Capability `app.quit` in `registry/capabilities.json`: an instance reports it exactly when it implements `app.quit`. An older instance does not report it, and a client then tells the end user to save the project and close the window.
- Reasons (the registry only grows): `job_in_progress` for `BUSY`, and `no_project_path` in the scope `null` (the same code that `INVALID_ARGUMENT` already has, for a `projectPath` that is null because the project was never saved).
- The vector member `endsSession` (`schemas/vector.schema.json`, `vectors/README.md`, "Vectors that end the instance"): a vector whose last step makes the instance quit by itself. A request vector with it has `connectionAfter` `closed` (the schema enforces that). The runner checks within 15 seconds that every connection is closed, the port accepts none, the discovery file is gone and, for a process it started, that it exited by itself with status 0. The format restarts the target rather than ordering the vectors: after such a vector the runner does not use the instance again, and a runner that shares an instance between vectors starts a new one.
- Vectors `app/quit-clean` and `app/quit-saved-path` (the result for a never saved project and for a saved one), `app/quit-dirty-discard` (discarded changes and `IRREVERSIBLE`), these three with `endsSession`; `app/quit-dirty-refused` (`UNSAVED_CHANGES(project_dirty)`, the instance keeps running), `app/quit-busy` (`BUSY(job_in_progress)`), `app/quit-busy-export` (`BUSY(export_in_progress)`), `app/quit-busy-modal` (`BUSY(modal_open)` ahead of `UNSAVED_CHANGES`, which shows the order of the checks), `app/quit-invalid` and `app/quit-capability-missing`.
- PROTOCOL.md: section 3.6 rule 2 (also `app.quit` makes the server stop), section 7 rule 6 (`app.quit` needs the editor window), section 13.2 (the job check of `app.quit` and `job_in_progress`), section 14.1 (the exception), section 20.2 rule 3 (the two methods that take `discardUnsaved`, and that `app.quit` is stricter than the window), section 22 (the capability, the L8 row and the method row).
- Side effect `tempoRounded` `{fromBpm, toBpm, revert}` (PROTOCOL.md section 14.6): when the tempo field of the transport bar holds the keyboard focus (a window in the foreground that has just started does), each time the window switches view, in both directions, the focus leaves the field, which writes the tempo it shows, rounded to one decimal, back to the project when the tempo has more than one decimal (a tempo of one decimal or none is left as it is, and a window whose field does not hold the focus, such as one in the background, may round nothing). A switch of `ui.setWorkspace`, or of `ui.setSelection` with `openEditor` true, then also lists the tempo in `changes` (entity `tempo`, member `bpm`, as `transport.setTempo` does), carries the recipe `transport.setTempo {bpm: fromBpm}` in the side effect (null when the instance does not report that capability) and has `dirty.after` true; the time signature is untouched and `revisionDiff` stays empty. The statements that a switch never marks the project as changed (PROTOCOL.md section 14.6 and section 21 rule 4, the descriptions of both methods) now name this exception. It is OpenTune's own behaviour, which a click on a view button has as well. Vector `ui/set-workspace-tempo-rounded`, which has the precondition `keyboardFocus` (next entry).
- Vector member `given.keyboardFocus` (`schemas/vector.schema.json`, `vectors/README.md`, "Preconditions"): `tempoField` means that the tempo field of the transport bar holds the keyboard focus, as in a window that has just started in the foreground. Without the member a vector assumes nothing about where the keyboard focus is. A runner that cannot make the field hold the focus (a started OpenTune whose window may be in the background) reports the vector as skipped with that reason. The vector `ui/set-workspace-tempo-rounded` has `keyboardFocus` `tempoField`. A runner of the OpenTune fork that cannot establish it gets a skipped vector, so it has to learn to.

### Removed

- Method `content.analyzeReference` (schema, entry of `methods/index.json`, PROTOCOL.md section 22). The capability `reference.v1` leaves the layer table of section 22 and no server reports it any more; its entry in `registry/capabilities.json` stays (see Changed). The job kind `referenceAnalysis` goes with them: PROTOCOL.md section 12.6 ("Reference analysis jobs") is replaced by a note that keeps its number, so that the numbers of the later sections stay as they were, and the table row of section 12.3, the sentence on repeated requests in section 12.5 and rule 8 of section 15.4 (the known defect of OpenTune's reference analysis) are gone. `common.schema.json` no longer lists the kind.
- `content.autoTune`: the mode `reference`, with its member `placementId` (no other mode took it), the `x-otcp.valueCapabilities` entry and the job it started. The method starts no job any more: `x-otcp.startsJob` is null and `x-otcp.jobErrors` and `$defs.jobResult` are gone. `noteCount` of the result is never null any more (it was null only in the result that handed the work to a job).
- `arrangement.edit`: the op `setReference` (`opSetReference`, `referencePlacementId`) and the reference binding of a clip in the descriptions of `arrangement.edit`, `arrangement.copy` and `track.duplicate`.
- `content.getDetails`: the result member `reference` (`referencePlacementId`, `alignmentReady`). `autoModes.available` lists no reference alignment, as `content.autoTune` has no such mode. `autoModes.uiButtonRuns` is still the mode that the AUTO button in the OpenTune window would run now, and the description of `content.getDetails` and PROTOCOL.md section 21 rule 1 say what that means in a build whose window still offers the reference alignment (a build from before OpenTune's upstream project removed it): while a reference track is bound, the button runs it and `uiButtonRuns` is `reference`, a value that is not in `autoModes.available`, and a client says that the button runs a mode the service cannot run. This is a revision of the text of this release candidate, not a new member: the schema allows any `camelName` there, as before.
- `project.get`: the placement member `referencePlacementId`. `project.open`: `skipped.referenceBindingCount`. `track.delete`: the result member `danglingReferences` and the `referencePlacementId` field in `changes`.
- `ui.setSelection`: the queued reference analysis (`sideEffects.referenceAnalysisQueued` and the warning `REFERENCE_ANALYSIS_QUEUED`); PROTOCOL.md section 14.6 and section 21 rule 3 lose their sentences.

### Clarified

- PROTOCOL.md section 15.3 rule 6, with the descriptions of `edit.undo`, `edit.redo` and `historyEntry`: a track deletion is a barrier in the undo and redo histories. An entry recorded through this API is possibly stale only when a deletion removed or moved down a track it addresses; such an entry fails without `force` with `UNDO_CONFLICT(stale_entry)`, and an entry whose tracks did not move is not possibly stale and is applied as usual, without a warning. An entry recorded in the UI is possibly stale after every deletion; without `force` it is applied with `UNDO_ENTRY_POSSIBLY_STALE`, and a call with `force`, which the end user asked for, applies it without that warning and clears `possiblyStale`. `origin` and `possiblyStale` therefore tell a client in advance which of the two happens. New vectors show these cases and the barrier set by `track.delete`.
- vectors/README.md: a runner decides whether a vector applies from the capabilities the instance reports before it establishes `given`; `withoutCapabilities` removes capabilities only while the vector runs.
- PROTOCOL.md sections 3.2 rule 3 and 3.3 rule 5: a JSON string, member names included, that escapes a lone surrogate is not valid JSON, so after authentication such a line gets `INVALID_ARGUMENT(parse_error)` with `id` null; the new vector `session/parse-error-lone-surrogate` shows it. This holds for every string of the line, also for the first value of a member name that appears twice, which a parser would drop.
- PROTOCOL.md section 5.5: on a normal stop the server may delete the ready file, but only while it still holds the `pid` and `instanceId` this instance wrote, so that it never deletes the ready file of a later start.
- PROTOCOL.md section 15.3 rule 6: an entry recorded through this API whose content a track deletion removed is applied as in the OpenTune UI: the step is used up and changes nothing (`noOp` with `UNDO_NO_EFFECT`).
- PROTOCOL.md section 15.3 rule 9 (new), with the descriptions of `edit.undo` and `edit.redo`: changes of a content without an undo entry (writes that are not undoable, notes generated as a side effect) are never taken back. Entries recorded through this API put back only the aspects of a content that their own change touched, and no longer those that a later change without an undo entry changed; such a change clears the redo history. A step left with nothing to put back is `noOp` with `UNDO_NO_EFFECT`.
- `import.start`: with `newTrack`, when every track holds clips, the call fails with `INVALID_ARGUMENT(track_capacity)` instead of importing onto the active track. Its revert recipe, which deletes the imported clips with `arrangement.edit`, carries `requiresConsent: true`, because deleting clips needs the end user's consent; the same holds for the revert recipe of `arrangement.copy`.
- `project.open`: its revert recipe carries no expected token; the dirty check (`UNSAVED_CHANGES(project_dirty)`) keeps it from overwriting later work.
- `content.getNotes`: `detectedMidi` is a fractional MIDI number, the pitch OpenTune shows for the note, to 0.01 semitone or finer.
- `content.getDetails`: `autoModes.uiButtonRuns` is `reference` only when the clip has a reference binding, the instance reports `reference.v1` and the experimental features are on.
- `content.editTimeGrid`: where seeded handles lie and the minimum spacing of moves are implementation-defined, as in OpenTune's time tool; clients read the handles instead of assuming values.
- Registries: the descriptions of `confirm_required` (also deleting clips), `dialog_commits_on_close` (consent member `confirm`), `track_capacity` (also `newTrack`) and `REPLACES_ALL_NOTES` (data `{removedCount, createdCount}`).

## [1.0.0-rc.1] - unreleased

First release candidate of protocol major 1, and the first version of the specification. It defines every method of layers L2 to L5; the methods of layers L6 and L8 and the UI-bridge methods are listed under "Planned". Changes made while this release candidate is drafted are folded into this entry; from the `spec-v1.0.0-rc.1` tag on, every change is recorded under the version that makes it.

### Added

- PROTOCOL.md: conventions; scope and non-goals; versioning and compatibility rules; transport and framing (literal `127.0.0.1`, OS-assigned port, one JSON message per line, a JSON-RPC 2.0 profile without batches or server-initiated messages, request ids decided by value and echoed as plain integer literals); limits; rules before authentication; `session.hello` with fixed failure responses and server-proof verification; discovery files and their lifecycle, with private file permissions on every system; enabling the control API; capabilities and registries; clocks and unit suffixes; handles, whose type prefixes (`c:`, `p:`, `u:`, `j:`) keep the kinds apart; revision tokens; the readiness gate; jobs and cancellation per job kind; concurrency, busy checks and UI priority; the write result envelope; undo descriptors, revert recipes (which never carry the user's consent) and undo rules; read conventions; errors; warnings; the export contract; paths, file identity, renames that never replace an existing target, and untrusted strings; editing schemes; the layer table and the index of all 43 methods.
- Number request ids are limited to integers from 0 to 2^53-1. An id only pairs a response with its request, so negative and fractional ids carry no meaning, and excluding them avoids differences between JSON parsers in how such numbers are read and written back.
- An entry created in the OpenTune UI gets an `undoId` when `edit.undo` or `edit.redo` applies it, so that the revert recipe of that step (`edit.redo` or `edit.undo`) can name it without `force`.
- `edit.undo` and `edit.redo` with `force` need no `expectedUndoId` and ignore it when it is given. A call with `force` that applies an entry clears its `possiblyStale`, so the revert recipe of such a step, which never carries `force`, is a complete request.
- Notes in `changes` and `created` of a write result are referenced at the revision after the write, notes in `removed` at the revision before it, so that every note reference names a note that exists at its revision.
- `export.start` with `ifExists` `error` fails at once with `ALREADY_EXISTS(target_exists)` when the target already exists, so that clients get the answer without a job.
- An export records the revisions of its contents when all of them are ready and it starts writing the file, so that a revision that changes while the export waits, for example because an analysis finishes, does not fail it with `REVISION_CONFLICT(changed_during_export)`.
- A revert recipe whose method needs a capability the instance does not report is not given: `revert` is null there and the result carries `IRREVERSIBLE`. Imports therefore name `arrangement.edit` in their recipes only on instances that report `arrangement.v1`.
- `import.start` takes an optional `idempotencyKey`: a repeated call with the key of a retained import job returns that job instead of importing the files again.
- A params value can need a capability besides its method's (`x-otcp.valueCapabilities`); AUTO in reference mode needs `reference.v1`.
