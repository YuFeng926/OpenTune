# Control API review checklist / 控制接口审核清单

本清单是控制接口任何改动的审核依据，范围是 `Source/Control/**`、`Source/Standalone/ControlEditorBridge*`、`Tests/Control/**`、`cmake/OpenTuneControl.cmake`，以及 [`README.md`](README.md)「Hooks」一节列出的接入钩子。OpenTune 的维护者、控制接口的贡献者，以及双方的 AI agent，审同一个改动时都照这份清单逐条核对。它与 [`README.md`](README.md)（设计与约定）、[`MIRRORS.md`](MIRRORS.md)（镜像）和规范副本 `Tests/Control/spec/otcp/v1/PROTOCOL.md` 一起使用。每一条有编号（例如 T3），审查意见引用编号即可；每一条都写明怎么查：看哪个文件、跑哪个测试、grep 什么。与本次改动无关的条目写「不涉及」，不要略过不提。

This checklist is the basis for reviewing any change to the control API: `Source/Control/**`, `Source/Standalone/ControlEditorBridge*`, `Tests/Control/**`, `cmake/OpenTuneControl.cmake` and the integration hooks listed in the "Hooks" section of [`README.md`](README.md). OpenTune's maintainers, the contributors of the control API and the AI agents of either side check the same change against it, item by item. Use it together with [`README.md`](README.md) (design and conventions), [`MIRRORS.md`](MIRRORS.md) (mirrors) and the specification copy `Tests/Control/spec/otcp/v1/PROTOCOL.md`. Every item has an id (for example T3) for review comments to cite, and says how to check it: which file to read, which test to run, what to grep. Answer an item that does not concern the change with "not applicable" rather than leaving it out.

## 0. Setup / 准备

- `<base>`：本次改动所基于的上游提交，例如 `git merge-base HEAD <上游分支>`。下文的 `git diff <base>...HEAD` 只看本次改动。
- 控制接口的测试只存在于两个选项都为 ON 的构建里（两者默认都是 OFF）：用你平常的 configure（`CMakePresets.json` 里的 preset 或自己的命令），加上 `-DOPENTUNE_ENABLE_CONTROL_API=ON -DOPENTUNE_BUILD_TESTS=ON`，构建后运行 `ctest --test-dir <构建目录> -C <配置> -R Control --no-tests=error`。下文的 `<构建目录>` 与 `<配置>` 都指它们：`<配置>` 是你构建的配置（例如 `Release`），多配置生成器（Visual Studio、Xcode、Ninja Multi-Config）必须带 `-C`，单配置生成器会忽略它。默认构建里没有这些测试；不加 `--no-tests=error` 时 ctest 找不到测试也返回 0。
- grep 一律用 `git grep`，只搜已跟踪的文件；路径限定写在 `--` 之后。

- `<base>`: the upstream commit the change is based on, for example `git merge-base HEAD <upstream branch>`. `git diff <base>...HEAD` below shows this change only.
- The control API's tests exist only in a build configured with both options ON (both are OFF by default): configure the way you usually do (a preset from `CMakePresets.json` or your own command) with `-DOPENTUNE_ENABLE_CONTROL_API=ON -DOPENTUNE_BUILD_TESTS=ON` added, then build and run `ctest --test-dir <build directory> -C <config> -R Control --no-tests=error`. Below, `<build directory>` and `<config>` mean these: `<config>` is the configuration you built (for example `Release`); a multi-config generator (Visual Studio, Xcode, Ninja Multi-Config) needs `-C`, and a single-config generator ignores it. A default build has none of these tests, and without `--no-tests=error` ctest exits 0 when it finds no test.
- Grep with `git grep`, which searches tracked files only; path limits go after `--`.

## 1. Threading and lifecycle / 线程与生命周期

- [ ] **T1** 工程内容只在消息线程读写。Ops 只经 `ControlOpContext`（`Ops/OpsRegistry.h`）拿到 processor 与 bridge，它在消息线程之外抛 `ControlThreadViolation`；通往消息线程的唯一通道是 `ControlMessageThread::post()` / `call()`（`ControlMessageThread.h`）。**查**：`git grep -n "MessageManager::callAsync(" -- Source/Control "Source/Standalone/ControlEditorBridge*" ":!*.md"` 只命中 `ControlMessageThread.cpp` 的两处调用；新方法用 `controlReadMethod`、`controlWriteMethod`、`controlJobMethod` 或 `controlOffMainThreadReadMethod` 注册，不自己开线程碰内容；跑 `ControlProcessorTests.ThreadProbe`、`ControlProcessorTests.Reads`。
- [ ] **T2** 不在消息线程运行的方法，只有 schema 写明 `x-otcp.mainThread: false` 的那些（dispatcher 里的现在是 `app.getLog`、`job.get`、`job.cancel`；`session.hello` 的 schema 也是 `false`，但它由服务端在进入 dispatcher 之前自己回答，不在方法表里）。它们拿不到 `ControlOpContext`，不读写内容、processor 或 bridge，只调用自身约定为线程安全的 OpenTune 函数。**查**：`ControlProcessorTests.OffMainThread`（方法表与 schema 的 `mainThread` 一致）；`ControlMethodTable::add()`（`Ops/OpsRegistry.cpp`）的断言。
- [ ] **T3** 网络线程（连接线程、`job.get` 的等待线程）等待消息线程时，不持有 processor 的任何锁或 lease，尤其是 `ProcessRenderRuntime::CompletionCallbackLease`。**查**：`git grep -n "CompletionCallbackLease\|MessageManagerLock" -- Source/Control "Source/Standalone/ControlEditorBridge*" ":!*.md"` 只命中 `ControlMessageThread.h` 的注释；读 `ControlDispatcher.cpp` 中调用 `call()` 前后的代码。
- [ ] **T4** 关闭合同。`ControlService::stop()`（`ControlService.cpp`）在消息线程上依次：置停止标志（新请求得到 `SHUTTING_DOWN`）→ `ControlMessageThread::stop()`（唤醒所有等待者，队列里的函数变成空操作）→ `ControlJobs::stop()`（等待中的 `job.get` 立即得到 `SHUTTING_DOWN`，销毁每个 job 的工作并 join 它拥有的线程）→ `ControlServer::stop()`（每次网络等待最多 `kPollIntervalMs` 即 250 ms，有界 join `kStopJoinTimeoutMs` 即 2000 ms，删除发现文件）→ 删除就绪文件 → 关闭日志门。它是幂等的，processor 析构函数的第一句调用它。**查**：读 `ControlService::stop()` 与 `ControlServer.cpp` 开头的常量；跑 `ControlProcessorTests.Shutdown`、`.RepeatedStop`、`.DestroyBeforeStart`、`.DispatchShutdown`、`.JobShutdown`、`.JobDisconnect`。
- [ ] **T5** 放弃标志。超过 `dispatchTimeoutMs` 仍未开始的请求，在它开始时要取的同一把锁下被标为放弃，回 `TIMEOUT(dispatch_timeout)`、`executed: false`，之后绝不执行；已经开始的照常完成并返回真实结果（PROTOCOL.md 13.1 第 2、3 条）。**查**：`ControlMessageThread::call()` 的 `CallResult::TimedOut` 与 `CallResult::Stopped`；`ControlProcessorTests.DispatchTimeout`、`.DispatchShutdown`。
- [ ] **T6** 投递到消息线程的每个函数都捕获存活令牌，服务停止或销毁之后什么也不做。启动由 `ControlService::scheduleStart()` 经 `post()` 投递；运行期未开启接口时什么也不投递。**查**：`ControlMessageThread.cpp` 里两处 `juce::MessageManager::callAsync` 调用都捕获共享状态 `shared`，而不是对象本身；`ControlProcessorTests.DestroyBeforeStart`、`.Disabled`。
- [ ] **T7** 经 `call()` 运行的函数不得同步停止控制服务（例如关闭应用或销毁 processor 的操作），只能在函数里用 `post()` 投递停止，然后返回；否则 `stop()` 要等到有界超时才结束 join。结束实例的操作（目前只有 `app.quit`）把退出步骤交给 `ControlOpContext::endInstanceAfterReply()`，由 dispatcher 在响应写出之后才投递，并在方法结果确定时就进入停止状态。**查**：读新操作中关闭应用或销毁 processor 的路径；对照 README「Threading rules」与「Quit」；跑 `ControlProcessorTests.AppQuitSequence`、`.AppQuitStopping`。
- [ ] **T8** job 的工作只在消息线程上逐 tick 推进，每一步很快返回，不跑嵌套消息循环；工作自己开的线程在析构时 join，`ControlJobs::stop()` 在消息线程上销毁全部工作。**查**：读新 job 的 work 函数与析构函数；`ControlProcessorTests.Jobs`、`.JobShutdown`。
- [ ] **T9** 控制接口的代码不在音频线程上运行，实时路径上不加锁、不分配内存、不做 I/O。**查**：`git diff <base>...HEAD -- Source/PluginProcessor.cpp` 中，`processBlock` 及其调用的函数里没有新增行。

- [ ] **T1** Project content is read and changed only on the message thread. Operations reach the processor and the bridge only through `ControlOpContext` (`Ops/OpsRegistry.h`), which throws `ControlThreadViolation` off the message thread; the only way to the message thread is `ControlMessageThread::post()` / `call()` (`ControlMessageThread.h`). **Check:** `git grep -n "MessageManager::callAsync(" -- Source/Control "Source/Standalone/ControlEditorBridge*" ":!*.md"` finds the two calls in `ControlMessageThread.cpp` only; a new method is registered with `controlReadMethod`, `controlWriteMethod`, `controlJobMethod` or `controlOffMainThreadReadMethod` and starts no thread of its own that touches content; run `ControlProcessorTests.ThreadProbe` and `ControlProcessorTests.Reads`.
- [ ] **T2** Only methods whose schema says `x-otcp.mainThread: false` run off the message thread (in the dispatcher now `app.getLog`, `job.get`, `job.cancel`; the schema of `session.hello` is `false` too, but the server answers it itself before the dispatcher, so it is not in the method table). They get no `ControlOpContext`, never read or change content, the processor or the bridge, and call only OpenTune functions that are thread-safe by their own contract. **Check:** `ControlProcessorTests.OffMainThread` (the method table matches each schema's `mainThread`); the assertion in `ControlMethodTable::add()` (`Ops/OpsRegistry.cpp`).
- [ ] **T3** A network thread (a connection thread, the waiter thread of `job.get`) that waits for the message thread holds no lock or lease of the processor, in particular no `ProcessRenderRuntime::CompletionCallbackLease`. **Check:** `git grep -n "CompletionCallbackLease\|MessageManagerLock" -- Source/Control "Source/Standalone/ControlEditorBridge*" ":!*.md"` finds only the comment in `ControlMessageThread.h`; read the code around the `call()` in `ControlDispatcher.cpp`.
- [ ] **T4** The stop contract. `ControlService::stop()` (`ControlService.cpp`) runs on the message thread, in this order: set the stop flag (new requests get `SHUTTING_DOWN`) → `ControlMessageThread::stop()` (wakes every waiter; queued functions become no-ops) → `ControlJobs::stop()` (waiting `job.get` requests get `SHUTTING_DOWN` at once; the work of every job is destroyed, joining the threads it owns) → `ControlServer::stop()` (every network wait polls at most `kPollIntervalMs`, 250 ms; bounded join `kStopJoinTimeoutMs`, 2000 ms; the discovery file is deleted) → delete the ready file → close the log gate. It is idempotent, and it is the first statement of the processor's destructor. **Check:** read `ControlService::stop()` and the constants at the top of `ControlServer.cpp`; run `ControlProcessorTests.Shutdown`, `.RepeatedStop`, `.DestroyBeforeStart`, `.DispatchShutdown`, `.JobShutdown`, `.JobDisconnect`.
- [ ] **T5** The abandon flag. A request that has not started within `dispatchTimeoutMs` is marked abandoned under the same mutex its start takes, answered with `TIMEOUT(dispatch_timeout)` and `executed: false`, and never runs later; a request that has started completes and returns its real result (PROTOCOL.md section 13.1 rules 2 and 3). **Check:** `CallResult::TimedOut` and `CallResult::Stopped` of `ControlMessageThread::call()`; `ControlProcessorTests.DispatchTimeout`, `.DispatchShutdown`.
- [ ] **T6** Every function posted to the message thread captures the liveness token and does nothing once the service has stopped or is destroyed. The start is posted by `ControlService::scheduleStart()` through `post()`; nothing is posted when the API is not enabled at run time. **Check:** both `juce::MessageManager::callAsync` calls in `ControlMessageThread.cpp` capture the shared state `shared`, not the object; `ControlProcessorTests.DestroyBeforeStart`, `.Disabled`.
- [ ] **T7** A function run through `call()` must not stop the control service synchronously (for example an operation that closes the application or destroys the processor); it posts the stop with `post()` and returns, otherwise `stop()` ends its join only at the bounded timeout. An operation that ends the instance (only `app.quit` now) hands its exit step to `ControlOpContext::endInstanceAfterReply()`, and the dispatcher posts it only after the response is written and enters the stopping state when the result is decided. **Check:** read the paths of a new operation that close the application or destroy the processor; compare with "Threading rules" and "Quit" in the README; run `ControlProcessorTests.AppQuitSequence` and `.AppQuitStopping`.
- [ ] **T8** The work of a job runs only on the message thread, one short step per tick, without a nested message loop; a thread that the work owns is joined in its destructor, and `ControlJobs::stop()` destroys every work on the message thread. **Check:** read the work function and the destructor of a new job; `ControlProcessorTests.Jobs`, `.JobShutdown`.
- [ ] **T9** Nothing of the control API runs on the audio thread; the real-time path takes no lock, allocates no memory and does no I/O. **Check:** `git diff <base>...HEAD -- Source/PluginProcessor.cpp` adds no line to `processBlock` or to the functions it calls.

## 2. Undo, dirty flag and tokens / 撤销、脏标记、令牌

- [ ] **U1** 接口产生的撤销条目用与界面相同的上游 `UndoAction` 类（例如 `PianoRollEditAction`、`PitchShiftEditAction`、`TimeGridEditAction`、`MultiMovePlacementAction`），外面包一层 `ControlOriginAction`（`Edit/ControlOriginAction.h`）。用户可以在界面里像撤销自己的编辑一样撤销它。**查**：`git grep -nE "(\.|->)addAction\(" -- Source/Control "Source/Standalone/ControlEditorBridge*"` 只命中 `Edit/ControlOriginAction.cpp`（`ControlHistory::record()`）；`git grep -n "public UndoAction" -- Source/Control ":!*.md"` 只有 `ControlOriginAction`。
- [ ] **U2** 一次调用最多一个撤销步（`undo.steps` 恒为 1）：一次调用的多次提交合进同一个 `ControlOriginAction`。**查**：一个方法每次调用最多调用一次 `ControlHistory::record()`；`ControlProcessorTests.AutoTune`（多个范围一步）、`.SnapNotes`、`.Arrangement`（多个 op 一个条目）、`.EditNotes`。
- [ ] **U3** 改变内容某一方面（音符、key、移调、时间网格）却没有撤销条目的写入，调用 `ControlHistory::onChangeWithoutEntry()`：之前经接口记录的条目不再还原该方面，并经钩子 `UndoManager::clearRedo()` 清空重做历史（PROTOCOL.md 15.3 第 9 条）。**查**：改变内容某一方面且调用 `setNotUndoable` 的新写入，同时调用 `onChangeWithoutEntry`（现有的三处调用在 `Ops/ContentTuneOps.cpp` 的两处与 `Ops/TimingOps.cpp` 的一处）；`ControlProcessorTests.Undo`、`.SetKey`。
- [ ] **U4** 标脏。每个随工程保存的改动之后调用 `controlMarkDirty()`（`Ops/WriteEnvelope.h`），界面不标脏的地方也要标（PROTOCOL.md 15.5）；结果的 `dirty` 报告调用前后的值。只改视图状态（不随工程保存）的写入不标。**查**：新写入方法里的 `controlMarkDirty`；`ControlProcessorTests.WriteEnvelope`、`.SetKey`、`.Timing`、`.Tracks`。
- [ ] **U5** 写结果里的令牌（`tokens`）与 `changes[].after` 都从提交后的状态读回，不用请求里的值或预测值：envelope 在 `committed()` 里读回经 `touchContent()` / `touchPlacement()` 登记的内容与片段的令牌，音符经 `controlReadCommittedNotes()` 读回。**查**：新方法里的 `touchContent` / `touchPlacement` 调用；测试把结果的令牌与随后一次读取比较（`ControlProcessorTests.EditNotes`、`.Timing`、`.ArrangementCopy`）。
- [ ] **U6** `REVISION_CONFLICT` 的 reason 要指明是哪个方面变了：`content_changed`、`grid_changed`、`key_changed`、`geometry_changed`、`arrangement_changed`、`changed_during_export`、`cursor_stale`（`registry/reasons.json`）。写入只检查它依赖的那几个方面的令牌（`controlCheckExpectedTokens()`，`Ops/EditSupport.h`）。**查**：`git grep -n '"REVISION_CONFLICT"' -- Source/Control ":!*.md"` 的每一处 reason 都在注册表里；`ControlProcessorTests.TokenAspects`、`.TimingTokenAspects`、`.EditConflictRetry`。
- [ ] **U7** `edit.undo` / `edit.redo` 只在栈顶正是客户端点名的条目（`expectedUndoId`）时才执行，否则回 `UNDO_CONFLICT(top_mismatch)` 且不改任何东西；`force` 只在最终用户明确要求时使用；栈顶是片段切分、合并或删除时回 `UNSUPPORTED(undo_unsafe_build)`。**查**：`Ops/UndoOps.cpp`；`ControlProcessorTests.Undo`、`.ArrangementUndo`、`.TrackBarrier`。
- [ ] **U8** 上游新增 `UndoAction` 子类或改了已有子类时，确认接口的撤销识别仍然成立：`edit.undo` 的结果由前后两次快照描述（`controlDescribeEffect()`，`Ops/EditSupport.h`），`ControlOriginAction` 记录它还原的内容与方面。**查**：`git diff <base>...HEAD -- Source | grep -n "UndoAction"`；跑 `ControlProcessorTests.Undo` 与用到该动作的场景。

- [ ] **U1** The undo entries of the API use the same upstream `UndoAction` classes as the UI (for example `PianoRollEditAction`, `PitchShiftEditAction`, `TimeGridEditAction`, `MultiMovePlacementAction`), wrapped in a `ControlOriginAction` (`Edit/ControlOriginAction.h`), so the user can undo them in the UI like their own edits. **Check:** `git grep -nE "(\.|->)addAction\(" -- Source/Control "Source/Standalone/ControlEditorBridge*"` finds `Edit/ControlOriginAction.cpp` only (`ControlHistory::record()`); `git grep -n "public UndoAction" -- Source/Control ":!*.md"` finds `ControlOriginAction` only.
- [ ] **U2** One call is at most one undo step (`undo.steps` is always 1): several commits of one call go into one `ControlOriginAction`. **Check:** a method calls `ControlHistory::record()` at most once per call; `ControlProcessorTests.AutoTune` (several ranges in one step), `.SnapNotes`, `.Arrangement` (several ops in one entry), `.EditNotes`.
- [ ] **U3** A write that changes an aspect of a content (notes, key, pitch shift, time grid) without an undo entry calls `ControlHistory::onChangeWithoutEntry()`: entries recorded through the API before it no longer put that aspect back, and the redo history is cleared through the hook `UndoManager::clearRedo()` (PROTOCOL.md section 15.3 rule 9). **Check:** a new write that changes an aspect of a content and calls `setNotUndoable` also calls `onChangeWithoutEntry` (the three existing calls are two in `Ops/ContentTuneOps.cpp` and one in `Ops/TimingOps.cpp`); `ControlProcessorTests.Undo`, `.SetKey`.
- [ ] **U4** The dirty flag. Every change that is saved with the project is followed by `controlMarkDirty()` (`Ops/WriteEnvelope.h`), also where the UI does not mark the project (PROTOCOL.md section 15.5); `dirty` in the result reports the flag before and after. A write that changes only view state (not saved with the project) does not mark it. **Check:** `controlMarkDirty` in a new write; `ControlProcessorTests.WriteEnvelope`, `.SetKey`, `.Timing`, `.Tracks`.
- [ ] **U5** The `tokens` and every `changes[].after` of a write result are read back from the committed state, never taken from the request or the prediction: in `committed()` the envelope reads back the tokens of the contents and clips registered with `touchContent()` / `touchPlacement()`, and notes are read back with `controlReadCommittedNotes()`. **Check:** the `touchContent` / `touchPlacement` calls of a new method; the tests compare the result's tokens with a read that follows (`ControlProcessorTests.EditNotes`, `.Timing`, `.ArrangementCopy`).
- [ ] **U6** The reason of `REVISION_CONFLICT` names the aspect that changed: `content_changed`, `grid_changed`, `key_changed`, `geometry_changed`, `arrangement_changed`, `changed_during_export`, `cursor_stale` (`registry/reasons.json`). A write checks only the tokens of the aspects it depends on (`controlCheckExpectedTokens()`, `Ops/EditSupport.h`). **Check:** every reason at `git grep -n '"REVISION_CONFLICT"' -- Source/Control ":!*.md"` is in the registry; `ControlProcessorTests.TokenAspects`, `.TimingTokenAspects`, `.EditConflictRetry`.
- [ ] **U7** `edit.undo` / `edit.redo` apply the top entry only when it is the entry the client names (`expectedUndoId`), otherwise `UNDO_CONFLICT(top_mismatch)` and nothing changes; `force` is used only on the end user's explicit request; a clip split, merge or delete on top gives `UNSUPPORTED(undo_unsafe_build)`. **Check:** `Ops/UndoOps.cpp`; `ControlProcessorTests.Undo`, `.ArrangementUndo`, `.TrackBarrier`.
- [ ] **U8** When an `UndoAction` subclass is added or changed upstream, confirm that the API still recognises undo steps: the result of `edit.undo` is described from snapshots before and after (`controlDescribeEffect()`, `Ops/EditSupport.h`), and `ControlOriginAction` records the content and aspect it puts back. **Check:** `git diff <base>...HEAD -- Source | grep -n "UndoAction"`; run `ControlProcessorTests.Undo` and the scenarios that use the action.

## 3. Write envelope and revisionDiff / 写信封与 revisionDiff 的完整性

- [ ] **W1** 每个写都用 `ControlWriteEnvelope`（`Ops/WriteEnvelope.h`）构建结果，以 `committed()`、`predicted()`（dryRun）或 `handedToJob()` 之一结束。检查顺序：句柄 → 忙碌（`controlCheckBusy()`）→ 就绪门（`controlCheckContentReady()`）→ 期望令牌 → 方法自己的校验，任一失败都回 `controlOpError()`、`executed: false`（PROTOCOL.md 13.1 第 4 条）。**查**：读新方法的 run 函数；`ControlProcessorTests.WriteEnvelope`、`.BusyMatrix`。
- [ ] **W2** 每个写结果都带 `revisionDiff`，包括 `edit.undo`、`edit.redo` 与选择的改变；`revisionDiff` 里的每个变化都能由 `changes`、`created`、`removed` 或 `sideEffects` 解释（PROTOCOL.md 14.4 第 4、6 条）。交给 job 的写在交出前不改任何东西（调试构建断言此时 `revisionDiff` 为空）；job 的结果可以只报告它碰过的内容（`limitDiffToTouchedContents()`）。**查**：在场景里对照结果的 `revisionDiff` 与 `changes`；`ControlProcessorTests.WriteEnvelope` 与该方法的场景。
- [ ] **W3** noOp。提交了、但没有登记任何改变或副作用且 `revisionDiff` 为空的写，结果为 `noOp: true`；撤销描述用方法设定的那个，没有设定时 reason 为 `no_op`。noOp 是成功，不是错误。**查**：`ControlWriteEnvelope::committed()`；该方法场景里的 no-op 用例。
- [ ] **W4** sideEffects。超出目标实体的效果都登记为副作用（`addSideEffect()`），各带自己的 `revert`；引起重新渲染的写报告 `reRenderQueued`（`controlAddReRenderQueued()`）。dryRun 列出的 `changes` 与 `sideEffects` 与真正提交时一致。**查**：`ControlProcessorTests.AutoTune`（dryRun 的 `sideEffects` 等于提交的）、`.EditNotes`（预测等于提交）。
- [ ] **W5** 不可撤销。`setNotUndoable(reason, revert)` 的 reason 来自 `registry/reasons.json` 的 `undo` 范围。只要本实例有某个请求能还原状态，就必须给还原方法（`controlRevertRecipe()`）；只有确实无法还原，或还原方法需要本实例没有上报的能力（`controlReportsCapability()`）时，`revert` 才为 null。还原方法不带同意参数（`confirm`、以 `discard` 开头的成员），需要同意的标 `requiresConsent: true`。既不能撤销也不能还原的改变带 `IRREVERSIBLE` 告警（视图状态 `not_persisted_state` 与 `no_op` 除外）。**查**：每处 `setNotUndoable` 调用；`ControlProcessorTests.WriteEnvelope`（`IRREVERSIBLE`）与 C3 列出的还原往返测试。
