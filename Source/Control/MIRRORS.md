# Mirrored upstream functions / 被镜像的上游函数

[`mirror-map.json`](mirror-map.json) is the source of truth; the table below is generated from it and
`ControlMirrorDriftTests` fails when the two differ. The README's "Mirrors" section explains the idea.

[`mirror-map.json`](mirror-map.json) 是正本；下面的表由它生成，两者不一致时 `ControlMirrorDriftTests` 会失败。思路见 README 的「Mirrors」一节。

## What a mirror is / 什么是镜像

Some of what OpenTune's UI does is code in the UI classes (the piano roll, the editor, the processor's
export functions). The control API must not change those classes, so it repeats the UI's steps in
`Source/Control/**` and calls only the lower-level functions that already exist. That repeated code is a
**mirror**. When the upstream function changes and the mirror does not, the API quietly behaves differently
from the UI.

界面里的一部分行为写在界面类里（钢琴卷帘、编辑器、processor 的导出函数）。控制接口不能改这些类，所以在
`Source/Control/**` 里照界面的步骤另写一份，只调用已有的底层函数。这份重复的代码就是**镜像**。上游函数改了而镜像没跟着改，
接口的行为就会悄悄偏离界面。

## If you changed a function in the table / 改了表里的函数怎么办

1. Run `ControlMirrorDriftTests`. It exists only in a build configured with both options ON (both are OFF
   by default): configure the way you usually do (a preset from `CMakePresets.json` or your own command)
   with `-DOPENTUNE_ENABLE_CONTROL_API=ON -DOPENTUNE_BUILD_TESTS=ON` added, build, then run
   `ctest --test-dir <build directory> -C <config> -R ControlMirrorDrift --no-tests=error` (`<config>` is
   the configuration you built, for example `Release`; a multi-config generator needs `-C`). In a build
   without the two options there is no such test, and without `--no-tests=error` ctest would still exit 0.
   A red result names the function you changed, the file of `Source/Control` to bring in line, and the
   tests to run.
2. Read the change, and make the same change in the mirrored code in the "Control API" column. If the
   change is meant to alter what the UI does, the API must do the same; if it does not, say so in the commit.
3. Run the tests of the "Tests" column (the failure message prints the `ctest -R` expression).
4. Record the new hash: run the test executable with `--update`. It rewrites the hash in
   `mirror-map.json` and regenerates the table in this file. Commit all three files together. Updating the
   hash without step 2 defeats the purpose.

1. 运行 `ControlMirrorDriftTests`。它只存在于两个选项都为 ON 的构建里（默认都是 OFF）：用你平常的 configure（`CMakePresets.json` 里的 preset 或自己的命令），加上 `-DOPENTUNE_ENABLE_CONTROL_API=ON -DOPENTUNE_BUILD_TESTS=ON`，构建后运行 `ctest --test-dir <构建目录> -C <配置> -R ControlMirrorDrift --no-tests=error`（`<配置>` 是你构建的配置，例如 `Release`；多配置生成器必须带 `-C`）。没有这两个选项的构建里没有这个测试，不加 `--no-tests=error` 时 ctest 仍返回 0。变红时，输出会写明你改了哪个函数、要同步 `Source/Control` 的哪个文件、要跑哪些测试。
2. 读懂改动，在「Control API」一列的镜像代码里做同样的改动。若这次改动本来就要改变界面的行为，接口也必须一样；若不是，在提交里说明。
3. 跑「Tests」一列的测试（失败信息里有现成的 `ctest -R` 表达式）。
4. 记录新哈希：用 `--update` 运行测试可执行文件。它会改写 `mirror-map.json` 里的哈希并重新生成本文件的表。三个文件一起提交。没做第 2 步就更新哈希，等于白锁。

## How the hash is made / 哈希怎么算

The file is read as UTF-8 without a BOM and with LF line endings. Then, for a function (`fn-v1`) the
text from the line that holds its qualified name followed by `(` to the line of the `}` that closes its
body; for a declaration (`stmt-v1`) the text from the line that holds the given text to the first `;`
outside brackets. Braces, parentheses and quotes inside comments, string literals and character literals do
not count. Every line then loses its leading and trailing white space, empty lines are dropped, runs of
blanks and tabs become one space, and the lines are joined with LF. The hash is the lower-case hexadecimal
sha256 of those bytes.

So a change of indentation, line breaks, blank lines or line endings is not a drift, and a change of
logic is. Comments are part of the text on purpose: a changed comment is cheap to review and often says
that the behaviour changed.

先把文件按 UTF-8（去掉 BOM）读入，换行统一为 LF。函数（`fn-v1`）取从含限定名加 `(` 的那一行到函数体结尾 `}` 所在行的文本；声明（`stmt-v1`）取从含给定文字的那一行到括号之外第一个 `;` 的文本。注释、字符串字面量与字符字面量里的括号和引号不计。然后每行去掉首尾空白、删除空行、把连续的空格和制表符合并成一个空格，用 LF 连接。哈希是这些字节的小写十六进制 sha256。

因此只改缩进、换行、空行或换行符不算漂移，改逻辑算。注释有意保留在文本里：注释变了，复审的代价很小，而且常常说明行为变了。

## Adding a mirror / 新增镜像

When you add code to `Source/Control/**` that repeats the steps of an upstream function:

1. Add an entry to `mirror-map.json`: `upstream.file` and `upstream.symbol` (the qualified name; add the
   parameter types in parentheses to tell overloads apart), `kind` (`function` or `statement`) and
   `normalization` (`fn-v1` or `stmt-v1`), the Control files and symbols, the tests that cover the mirror,
   and a one-line note in English and Chinese. Put a placeholder in `sha256`: 64 lower-case hexadecimal digits that differ from every other entry
   (for example 63 zeros and one distinct digit), because the test checks the format before `--update` runs.
2. Run the test executable with `--update` to fill in the hash and generate the table row.
3. Name the upstream function in the comment of the mirrored code, and list it in the README.

在 `Source/Control/**` 里新增照搬上游函数步骤的代码时：

1. 在 `mirror-map.json` 加一条：`upstream.file` 与 `upstream.symbol`（限定名；要区分重载时在括号里写参数类型）、`kind`（`function` 或 `statement`）与 `normalization`（`fn-v1` 或 `stmt-v1`）、接口层的文件与符号、覆盖这处镜像的测试、一行中英文说明。`sha256` 先填占位值：64 位小写十六进制，且与其他条目都不同（例如 63 个 0 加一个互不相同的数字），因为测试在 `--update` 之前就会检查格式。
2. 用 `--update` 运行测试可执行文件，补上哈希并生成表中的行。
3. 在镜像代码的注释里写明对应的上游函数，并在 README 里列出。

## What the test checks / 测试检查什么

- every hash of `mirror-map.json` against the source tree (a moved or renamed function is reported as
  well, and then the entry is corrected by hand);
- the table in this file against `mirror-map.json`;
- that the Control files and symbols and the tests named there exist;
- that a change inside a mirrored function turns the check red and a change of formatting does not (on
  temporary copies of the upstream files, for every entry).

- `mirror-map.json` 里的每个哈希与源码树是否一致（函数被移动或改名也会报告，这时手工修正条目）；
- 本文件的表与 `mirror-map.json` 是否一致；
- 其中的接口层文件、符号与测试是否存在；
- 被镜像函数内部的改动会让检查变红、只改格式则不会（对每个条目，在上游文件的临时副本上验证）。
